# 排查记录 01：5000 rps 时延迟暴涨（TCP 连接反复重建）

- 日期：2026-10-19
- 环境：Mac (M4 Pro) 上的 UTM 虚拟机 rocky9-lab，Rocky Linux 9.8 aarch64，4 vCPU / 4GB；
  JDK 21；竞价服务和压测程序**运行在同一台虚拟机**上（共享 CPU，见"局限"）
- 服务：`rtb-bidder.service`（systemd），JDK 内置 HttpServer，8 个工作线程
- 压测：`LoadGen` 开环固定速率，超时 50ms，每轮 20 秒（另有 5 秒预热）

## 1. 现象

| 速率 | P50 | P90 | P99 | P99.9 | 超时 | 连接错误 | CPU 空闲 |
|---|---|---|---|---|---|---|---|
| 1000/s | 0.617 ms | 1.570 | 6.787 | 15.980 | 0 | 0 | 85% |
| 3000/s | 0.272 ms | 0.321 | 1.411 | 8.679 | 0 | 0 | 76% |
| **5000/s** | **45.917 ms** | 56.239 | 59.989 | 65.155 | 0 | **116** | **67%** |

5000/s 时延迟恶化约 170 倍，但 CPU 还有大量空闲 ⇒ 瓶颈不在 CPU。

## 2. 定位过程

| 检查 | 命令 | 结果 | 结论 |
|---|---|---|---|
| 服务端自身处理耗时 | `curl :8080/metrics`（延迟直方图） | 99.7% 的请求 ≤ 0.1 ms | 竞价逻辑不慢，时间花在别处 |
| TCP 连接状态 | `ss -s`；`ss -tan '( sport = :8080 or dport = :8080 )'` | **13,678 个 TIME-WAIT**，约 400 个 ESTAB | 连接没有复用，在不停地关闭和新建 |
| 进程 CPU 构成 | `pidstat -u -p <java pids> 1 3` | 压测进程 %system 45.7%，服务端 %system 15.7% | 大量时间花在内核态处理 TCP 建连 / 断连 |

## 3. 根因

JDK 内置 `HttpServer` 默认最多保留 **200** 个空闲长连接（`sun.net.httpserver.maxIdleConnections=200`）。
高并发下客户端同时持有约 400 个连接，超过上限的连接在请求结束后被服务端主动关闭；
客户端只能重新三次握手建连 ⇒ 每个请求多付建连开销、产生大量 TIME-WAIT、内核态 CPU 上升 ⇒
请求变慢 ⇒ 需要更多并发连接 ⇒ 恶性循环。

## 4. 修复

`deploy/rtb-bidder.service` 的 `JAVA_OPTS` 增加 `-Dsun.net.httpserver.maxIdleConnections=2000`（只改这一个变量）。

## 5. 修复后（5000/s）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| P50 | 45.917 ms | **0.251 ms** |
| P90 | 56.239 ms | 0.329 ms |
| P99 | 59.989 ms | **5.554 ms** |
| P99.9 | 65.155 ms | 23.195 ms |
| 连接错误 | 82~116 | **0** |
| TIME-WAIT（压测中） | 13,678 | 2,375 |
| 服务端 %system | 15.67% | 9.67% |

## 6. 局限与后续

- 压测程序和服务在同一台 4 核虚拟机上，互相抢 CPU（压测进程自己就用了 65~71%），
  P99 / P99.9 的长尾有一部分来自压测端。下一步：把压测程序放到另一台机器上（第二台虚拟机或 EC2）。
- 还剩约 2,000 个 TIME-WAIT：说明仍有少量连接在重建，待查（客户端连接池行为？）。
- 真实系统一般在竞价服务前面放负载均衡，并在客户端和服务端两侧显式配置长连接与连接池大小。

## 学到的知识点

- TIME-WAIT 是主动关闭连接的一方要停留的状态（Linux 上 60 秒），大量出现说明连接在频繁重建。
- 先看服务端自己的耗时，再看连接和内核态时间，可以快速区分"业务慢"和"基础设施慢"。
- 开环压测（按计划时间计时）才能暴露这种排队式的恶化；闭环压测会掩盖它。
