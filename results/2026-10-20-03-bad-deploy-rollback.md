# 记录 #03：坏版本发布演练——自动回滚，以及把中断从 28 秒降到 3 秒

- 日期：2026-10-20
- 环境：UTM 虚拟机 Rocky 9.8 aarch64，4 vCPU / 4 GB（个人实验环境，非生产），单台机器
- 工具：[`ansible/deploy.yml`](../ansible/deploy.yml)、[`ansible/tasks/activate_release.yml`](../ansible/tasks/activate_release.yml)

## 要验证什么

发布一个**启动就崩溃**的版本时：

1. 发布流程能不能自己发现问题；
2. 能不能自动回到上一个版本；
3. 用户（这里是压测程序）实际受到多大影响。

## 发布流程

```
build.yml   按 git 提交号打包 bidder-<版本>.tar.gz + SHA256
deploy.yml  校验 SHA256 → 解压到 releases/<版本>/ → 切换 current 符号链接 → 重启
            → 健康检查（/health 返回的版本号必须对得上）→ 冒烟测试（真实的 /bid 请求）
            → 任何一步失败：切回上一个版本，重复同样的检查，最后把本次发布标记为失败
```

## 坏版本

模拟一种常见的真实事故：新代码依赖一个新的环境变量，但生产配置里没有设置。

```java
String region = System.getenv("BIDDER_REGION").trim();   // 变量不存在 → NullPointerException
```

演练期间，压测程序持续以 500 次/秒发送请求，覆盖整个发布过程。

## 第一轮：只靠健康检查判断

- 坏版本启动后不到 1 秒就崩溃，systemd 每 2 秒自动重启一次（`Restart=on-failure`、`RestartSec=2`），每次都崩
- 健康检查重试 20 次（每次 1 秒）才放弃，然后回滚
- 坏版本一共崩溃了 13 次

**结果：服务中断约 28 秒，13,967 个请求失败（连接被拒绝）。** 回滚本身没有问题，但发现问题太慢。

## 改进：发现反复崩溃就立刻失败

systemd 会记录服务的自动重启次数 `NRestarts`（手动 `systemctl restart` 时归零）。发布后只要它大于 0，就说明新版本启动后崩溃过，没有必要再等健康检查：

```bash
restarts=$(systemctl show -p NRestarts --value rtb-bidder)
if [ "$restarts" -gt 0 ]; then echo "新版本启动后崩溃"; exit 1; fi
```

健康检查的间隔也从 1 秒缩短到 0.5 秒。

## 第二轮：同样的坏版本、同样的流量

| | 第一轮 | 第二轮（改进后） |
|---|---|---|
| 判定失败用时 | 约 20 秒 | 约 2 秒（systemd 第一次自动重启时） |
| 服务中断 | 约 28 秒 | **约 3 秒** |
| 失败的请求 | 13,967 | **1,530**（减少约 89%） |
| 最终状态 | 自动回到 `93b5e7115a` | 自动回到 `93b5e7115a` |

Ansible 输出（第二轮）：

```
新版本启动后崩溃，已被 systemd 自动重启 1 次。
版本 93b5e7115a-dirty-20261020135054 没有通过检查，自动回滚到 93b5e7115a
版本 93b5e7115a-dirty-20261020135054 发布失败，已自动回滚到 93b5e7115a，服务正常。
```

## 正常发布和手动回滚

同样在 500 次/秒的流量下：`rollback.yml` 回到上一个版本，再用 `deploy.yml` 发布回来，两次切换一共 147 个请求失败，**平均每次切换中断约 0.15 秒**。

这是单台机器上重启进程的固有代价：旧进程停了、新进程还没开始监听端口的那一小段时间。要做到零中断，需要至少两台机器放在负载均衡后面：先把一台从负载均衡上摘下来，发布、检查通过后再挂回去，然后发布下一台（`deploy.yml` 已经是 `serial: 1` 逐台发布）。这一步在上 EC2、加上 NLB 后做。

另外观察到：切换后的一小段时间里 P99.9 升高到约 200 ms。新启动的 JVM 还没完成 JIT 编译，处理得比较慢，属于"冷启动"。还没有专门验证，以后可以对比"切换前先预热"的效果。

## 演练中我自己犯的一个错误

前两次演练时，压测数据显示"0 个连接错误"，和服务中断明显矛盾。查了以后发现，压测在发布开始之前就已经结束了：

```bash
ssh rocky9 'cd ~/rtb-lab && nohup java ... > log 2>&1 &'
```

`&` 放到后台的是整个 `cd && java` 组合。bash 为它开了一个子 shell，这个子 shell 继承了 ssh 的输出通道，所以 ssh 一直等到压测结束才返回，接着才开始发布。

修正：让压测作为一个独立的后台任务运行，**先确认它确实在运行**，再开始发布。

教训：数据和预期对不上时，先怀疑测量方法。这两次的结果没有采用。

## 结论

- 版本化发布 + 自动回滚有效：坏版本不会留在线上，不需要人工介入。
- 判断"新版本坏了"要用多个信号：健康检查只能说明"还没好"，systemd 的重启次数能立刻说明"已经崩了"。
- 单台机器无法避免重启造成的短暂中断，零中断要靠多台机器加负载均衡。
